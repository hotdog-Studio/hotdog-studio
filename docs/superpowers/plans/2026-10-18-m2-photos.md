# hotdog.studio M2 (Photos) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build milestone M2 of hotdog.studio:

- the photo pipeline: validation, the EXIF allowlist, AVIF and WebP derivatives with no metadata, a cache and the manifest;
- committed fixture photos that double as a privacy negative control;
- the `/photos` index, album pages that work without JavaScript, the lightbox, and the home page's latest photos.

It starts with the shared CSS pass and the five design changes agreed at the M1 check-in.

**Architecture:** `scripts/photos/process.ts` runs before `astro dev` and `astro build`. It reads album folders from `PHOTOS_DIR`, or from `fixtures/photos` in fixture mode, and validates them. It then writes:

- stripped derivatives to `public/photos/`;
- a manifest, validated with Zod, to `src/generated/photos.json`;
- a placeholder stylesheet to `src/generated/photo-placeholders.css`.

Pages read the manifest through one adapter at build time. They never import it statically, because `lint` runs before any build. Pages pass plain props to components. The lightbox is one external module script on album pages, and it enhances thumbnail links that already work without JavaScript.

**Tech Stack:** Everything from M1 (Astro 7.4, TypeScript 6.0, Zod 4 via `astro/zod`, Vitest 5, Playwright 1.64, ESLint 10, Prettier 3, tsx, Node 24 LTS), plus sharp 0.35.5, exifr 7.1.3 and @astrojs/markdown-satteri 0.4.4.

**Spec:** `docs/superpowers/specs/2026-10-14-hotdog-studio-portfolio-design.md`. This plan covers §16 M2. That is §4.2 item 5, §4.5, §4.6, §5.5, §6, the photo parts of §7, §8.1 principle 3, the photo and negative-control tests in §8.2, the photo, home and no-JavaScript tests in §8.3, and the `dev` and `build` changes in §9. It also covers two sections of `docs/superpowers/notes/2026-10-17-m1-followups.md`: "M1 visual check-in" and "M2 (photos)".

It does not cover these, which belong to later milestones:
- **M3:** album Open Graph images.
- **M4:** the visual baselines, the privacy-scan gate and the quality summary.
- **M5:** the a11y, Lighthouse and container gates, and nginx.

  Install all three with `npm install -D`.
- **TypeScript is `astro/tsconfigs/strictest`.** `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` are on. An optional field that can receive `undefined` is typed `?: T | undefined`, as in M1.
- **CSP, from §10.2:**
  - no `style="…"` attributes;
  - no `<style is:inline>` or `<script is:inline>`;
  - no `set:html`.
- **Script inlining.** Set `vite.build.assetsInlineLimit: 0`. Astro's script plugin inlines a script chunk only when its size is below this limit, so 0 means never. This was verified: a built page then gets `<script type="module" src="/_astro/…js">`.
- **JavaScript.** Only `/photos/<album>` pages ship JavaScript: exactly one `<script type="module" src>`, and no inline script. Every other page ships none.
- **Generated files.**
  - `src/generated/photos.json` and `src/generated/photo-placeholders.css` are gitignored build outputs.
  - The JSON is read only through `loadPhotoManifest()` (Task 9), never by `import`.
  - The CSS is imported only by pages, never by components. This was verified: `astro check` passes while the file is missing, and the build bundles it into a hashed `/_astro/*.css`.
- **Only pages call `loadPhotoManifest()`.** This matches M1's rule for `@site-config` and `astro:content`. Components get everything through props.
- **Pipeline privacy (§6.3).** In `scripts/photos/`, never call sharp's `keepMetadata`, `withMetadata`, `keepExif`, `withExif`, `keepIccProfile` or `withIccProfile`. A unit test scans the source for them. sharp's default output carries no EXIF, XMP, IPTC or ICC data (verified for AVIF and WebP). Only `scripts/fixtures/` writes metadata.
- **exifr (verified):**
  - Always read with `exifr.parse(bytes, { pick: [...EXIF_TAGS], reviveValues: false })`.
  - `reviveValues: false` keeps `DateTimeOriginal` as the raw string `'YYYY:MM:DD HH:MM:SS'`. The default turns it into a `Date` in local time, which shifted 09:30 to 08:30Z on this machine.
  - exifr names tag 0xA431 (BodySerialNumber) `SerialNumber`, and returns ISO as `ISO`.
  - `exifr.gps()` returns `{ latitude, longitude }`.
  - On a file without EXIF, exifr returns `undefined` for JPEG, PNG and TIFF, but **throws** on WebP.
- **sharp (verified):**
  - `metadata().autoOrient` gives the size after orientation is applied: an Orientation 6 original stored at 900×600 reports `{ width: 600, height: 900 }`.
  - `stats().dominant` is quantised to bin centres: `#c89818` comes back exactly, but `#336699` comes back as `#386898`.
- **YAML.** The `yaml` package's default core schema keeps an unquoted `2025-06-14` as a string, and it ignores a leading BOM and CRLF line endings (verified). `album.yaml` dates therefore use `z.iso.date()`.
- **Copy and formats fixed by the spec:**
  - fallback alt: `<Album title>, photo <n> of <m>`;
  - EXIF line: `Sony A7 III · 35 mm · f/1.8 · 1/250 s · ISO 100`, with fields joined by ` · `;
  - lightbox counter: `3 / 24`;
  - album date: `Month YYYY` in en-GB, such as `June 2025`.
- **Copy fixed by this plan:**

  - empty index: "No albums are published yet."
- **URLs:** `/photos`, `/photos/<slug>`, `/photos/<slug>#<photoId>`, and derivatives at `/photos/<slug>/<id>-<width>.<avif|webp>`. None has a trailing slash.
- **Tests:**

## Decisions the spec leaves open (decided here, for Thomas to review with the plan)

1. **Drafts are filtered in the pipeline.**
   - A build never reads, encodes or publishes a draft album. Only `npm run dev` passes `--dev`, which includes them.
   - The manifest therefore has no `draft` field, which matches §6.5.
2. **`cover` and the `photos:` keys match filenames without regard to case,** because cameras write `DSC01234.JPG`.
3. **Ignored names.** The pipeline skips any name that starts with `.`, `@` or `#`, plus `Thumbs.db` and `desktop.ini` in any case. This extends §6.1's "hidden files" to Windows and NAS system files such as `@eaDir` and `#recycle`.
4. **Folders and stray files.**
   - An album folder may not contain other folders, once ignored names are skipped. A nested folder of photos fails the build rather than being skipped silently.
   - Plain files at the top of `PHOTOS_DIR` are ignored.
5. **The EXIF line shows camera, focal length, aperture, shutter and ISO,** as in the example in §4.6. The lens and the date are kept in the manifest (§6.5) but not shown.
6. **The camera name is the Model alone** when the Model's first word matches the Make's first word, ignoring case. Otherwise it is `Make Model`.
   - `Canon` with `Canon EOS R5` gives `Canon EOS R5`.
   - `NIKON CORPORATION` with `NIKON Z 6` gives `NIKON Z 6`.
   - `SONY` with `ILCE-7M3` gives `SONY ILCE-7M3`.
7. **Lightbox navigation.**
   - Previous and Next wrap round at either end.
   - A one-photo album has neither button.
   - Ctrl-, Cmd-, Shift- and Alt-clicks, and middle-clicks, keep the browser's default action.
8. **Home thumbnails deep-link.** Each "Latest photos" thumbnail links to `/photos/<album>#<photoId>`, so it opens that photo in the album's lightbox, or scrolls to its thumbnail without JavaScript. The section also links to the album.
9. **Neighbour preloading.**
   - It adds `<link rel="preload" as="image" imagesrcset imagesizes>` for the previous and next photos.
   - It uses the format the browser chose for the current photo, read from `currentSrc`, so it never fetches both AVIF and WebP.
   - The links can be asserted in e2e.
10. **Loading.**
    - The first three thumbnails on an album page and the first three covers on `/photos` load eagerly.
    - All others are `loading="lazy"`, including every thumbnail on the home page.
11. **Placeholder colours** are a `.ph-<id>` class per photo in the generated stylesheet.
12. **Encoding:**
    - AVIF at `quality: 55, effort: 4`;
    - WebP at `quality: 80`;
    - `PIPELINE_VERSION = 1`.
13. **Albums sort newest first;** albums with the same `date` sort by slug.
14. **No published albums.** A real build in which every album is a draft gives an empty `/photos` page with the empty-state line. The §6.6 "no albums" failure is about folders.

## Review Focus

1. **Upper-case camera extensions and case mismatches.** `DSC01234.JPG` on disk may be written `DSC01234.jpg` as a `photos:` key or as `cover`. The photo must be found and get its alt text. Test in Task 6.
2. **Windows and NAS system entries,** such as `Thumbs.db`, `desktop.ini`, `.DS_Store`, `@eaDir` and `#recycle`, at the top of `PHOTOS_DIR` or inside an album. They must be ignored, never reported as unsupported files or bad album names. Test in Task 6.
3. **The same export copied twice into one album,** such as `DSC01234.jpg` and `DSC01234 (1).jpg`. The bytes are identical, so the ids are too. The build must fail, naming both files, before it writes anything, rather than publishing duplicate ids that clash in derivative paths and lightbox hashes. Test in Task 8.
4. **An album URL whose hash is not a photo.** Examples are `#main`, left by the skip link, and a stale id after a re-export. The lightbox must stay closed, and nothing may throw. Test in Task 11.
5. **A one-photo album.** It must show no Previous or Next button, and the arrow keys must do nothing. The component test is in Task 11; there is no published one-photo fixture album, so the arrow-key guard is checked in review.

### Task 3: Photo manifest schema and display helpers

**Files:**
- Create: `src/lib/photos-schema.ts`, `src/lib/photos.ts`, `tests/support/photo-manifest.ts`
- Test: `tests/unit/photos-schema.test.ts`, `tests/unit/photos.test.ts`

**Interfaces:**
- **Produces from `photos-schema.ts`, the §6.5 manifest.** Every object is a `z.strictObject`, so any field §6.5 doesn't list fails validation, such as a leaked `gps` or `filename`. That makes the schema a second guard behind the EXIF allowlist.
  - `photoExifSchema` fields, all optional:

**Files:**

**Interfaces:**
- **Consumes:** the `data-lightbox-item` links from `PhotoGrid`.
- **`Lightbox` props:** `{ count: number }`. The markup:

  ```html
  <dialog class="lightbox" aria-label="Photo viewer" data-lightbox>
    <div class="bar">
      <p class="counter"></p>
      <button type="button" data-lightbox-close>Close</button>
    </div>
    <figure>
      <div class="picture" data-lightbox-picture></div>
      <figcaption><p class="caption" hidden></p><p class="exif" hidden></p></figcaption>
    </figure>
    <!-- Only when count > 1: -->
    <button type="button" data-lightbox-prev>Previous</button>
    <button type="button" data-lightbox-next>Next</button>
  </dialog>
  <script>import '../scripts/lightbox';</script>
  ```

  The script builds the `<picture>` itself, so the page has no `<img>` without a `src`.
- **`[album].astro`** renders `<Lightbox count={album.photos.length} />` after the grid.
- **Lightbox styles:**
  - **Layout:** the dialog fills the viewport. It sets `inline-size` and `block-size` to `100%`, removes the maximum sizes, and has no margin or border. Its background is transparent, and its text is `#ededed`.
  - **Backdrop:** `::backdrop { background: rgb(10 10 10 / 0.94); }`. This is near-black in both themes (§7), so every colour inside is fixed rather than a theme token.
  - **Image:** contained within the viewport, minus the bar and caption.
  - **Buttons:** at least 44px tall, light on dark at 4.5:1 or better.
  - **Focus:** `.lightbox :focus-visible { outline-color: #f2c230; }`.
  - **Scrolling:** `:global(:root:has(dialog[open])) { overflow: hidden; }` stops the page scrolling behind the dialog.
  - **Motion:** no transitions or animations at all (§4.6).
- **How `lightbox.ts` behaves.** The implementer writes the code; this is the contract.
  - **Setup:** it finds `dialog[data-lightbox]` and the `a[data-lightbox-item]` links, and does nothing if either is missing.
  - **Opening:**
    - A plain primary click on a thumbnail, with no Ctrl, Meta, Shift or Alt and `button === 0`, calls `preventDefault()` and opens the lightbox on that photo.
    - Any other click keeps the browser's default.
    - Enter on a focused link fires `click`, so the keyboard takes the same path.
  - **Showing photo `i`:**
    - It fills the picture with an AVIF `<source>` and a WebP `<source>`, both with `sizes="100vw"`.
    - The `<img>` gets the link's `href` as `src`, plus `width`, `height`, and the thumbnail image's `alt`.
    - The caption and the EXIF line are set, and each is `hidden` when empty.
    - The counter reads `` `${i + 1} / ${n}` ``.
    - It calls `history.replaceState(null, '', \`${location.pathname}${location.search}#${id}\`)`.
  - **Moving:**
    - Previous and Next, and the ArrowLeft and ArrowRight keys pressed in the dialog, move with wrap-around.
    - With one photo, the arrow keys do nothing.
  - **Closing:**
    - Close and Esc (the native `cancel`) both close the dialog.
    - On the `close` event, it removes the hash with `replaceState` and focuses the thumbnail that opened the lightbox.
  - **Deep links.** At start-up, if `location.hash` without the `#`, decoded, equals a thumbnail link's `id`, it opens on that photo, with that thumbnail as the opener. Any other hash is ignored.
  - **Preloading:**
    - After the image loads, it adds `<link rel="preload" as="image" imagesrcset imagesizes="100vw">` to `<head>` for the previous and next photos, once per photo.
    - It uses the AVIF srcset if `img.currentSrc` ends in `.avif`, and the WebP one otherwise.

- **`eslint.config.js`:** add `{ files: ['src/scripts/**'], languageOptions: { globals: globals.browser } }`.

## Carry-forward notes for the M3–M5 plans

- **Re-encoded photos keep their URLs (M5).** Derivative names are `<id>-<width>`, where the id hashes the original. Bumping `PIPELINE_VERSION` re-encodes the derivatives under the same URLs. Under §8.8's `immutable`, one-year cache on `/photos/*`, visitors would keep the old bytes for a year. Before the first deploy, either put the pipeline version in the path, such as `/photos/v1/<album>/…`, or accept that a re-encode needs a cache purge.
- **The real build needs `PHOTOS_DIR` (M5).** `npm run verify` must fall back to `fixtures/photos` with a loud notice (§9).
- **Lighthouse (M5).** Album pages must keep script bytes at or under 15 KB, and the newest album page comes from `src/generated/photos.json` (§8.7).
- **Accessibility (M5).** The axe gate's lightbox-open state (§8.5) should open the first photo of the newest album, by clicking it or with its `#id`.

- **Visual baselines (M4)** should include the lightbox open on `album-newer`.
- **SEO (M3).** An album's `og:image` is its cover's largest WebP.
- **Quality summary (M4).** `photosWithAlt` comes from the count of photos where `altIsFallback` is false.
