# hotdog.studio M1 (Skeleton) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build milestone M1 of hotdog.studio: a static Astro site with real and fixture build modes, validated content collections, the global layout, and the home, work and case-study pages. It comes with lint, unit and component tests, and functional e2e tests, and it ends at the visual check-in with Thomas.

**Architecture:** One switch, `SITE_MODE`, picks the content directory, the `@site-config` module and the output directory (`dist/` or `dist-fixtures/`). Content is Markdown and YAML in Astro content collections, validated by Zod schemas kept in `src/lib/` so they can be unit-tested on their own. A standalone checker enforces the rules that span the whole collection. Pages fetch data and hand it to components that take only props, so component tests never depend on Thomas's copy. Behaviour tests run Playwright against the fixture build.

**Tech Stack:** Astro 7.4 (static output), TypeScript 6.0 (strictest), Zod 4 via `astro/zod`, Vitest 5 with the Astro Container API and linkedom, Playwright 1.64, ESLint 10 (flat config), Prettier 3, tsx, Node 24 LTS.

**Spec:** `docs/superpowers/specs/2026-10-14-hotdog-studio-portfolio-design.md`. This plan covers §16 M1 and the parts of §3, §4.1–4.4, §5.1–5.4, §7, §8.1–8.3 and §9 (steps 1–6) that M1 needs. Photos (M2), about, 404, quality, SEO (M3), and all gates and containers (M4/M5) get their own plans after the M1 check-in.

- Only pages, `BaseLayout` and the `src/lib/case-studies.ts` adapter import `@site-config` or call `astro:content`. Components get everything through props.
- e2e behaviour tests run only against the fixture build (`dist-fixtures/`, served by `astro preview` on `:4321`).
- Playwright rules, enforced by eslint-plugin-playwright's recommended config:

## Deviations from the spec (Thomas confirms these at the M1 check-in)

1. **Prism instead of Shiki** (§4.4). In Astro 7.4, Shiki writes inline `style` attributes on `<pre>` and every token (verified), and `style-src 'self'` blocks those. Prism writes classes only, so we ship our own token stylesheet in the site palette. Highlighting still happens at build time, still with zero JS.
2. **TypeScript 6.0.3**, not the latest 7.0.2, because of the ceiling above.
3. **`astro.config.ts` instead of `.mjs`** (§12), so the Astro config and the content config share one `resolveSiteMode()`.
4. **The case-study rules live in `scripts/content/case-study-rules.ts`** (pure and unit-tested). `scripts/content/check-case-studies.ts` is the thin CLI the spec names.
5. **`other-projects.yaml` stays a plain list** of `{ name, description, repo }`. A loader `parser` adds positional ids. Without them, Astro's `file()` loader logs an error and builds an **empty** collection while the build still succeeds (verified).
6. **Fixture builds always show `local build` in the footer**, so the M4 visual baselines don't change with every CI build number.
7. **A placeholder `public/favicon.svg`** stands in until Thomas supplies the icon (§15). M3 generates the full favicon set.

## Review Focus

1. **CRLF line endings in case-study Markdown.** Thomas edits on Windows, so the checker must read frontmatter and headings the same way from `\r\n` files. Test in Task 4.
2. **A curly apostrophe in "What I’d change".** Smart-quote editors produce it, and it must count as the required heading. Test in Task 4.
3. **`## ` lines inside fenced code blocks, and the frontmatter's closing `---`.** Case studies are about code. Neither may be counted as an H2. A `---` straight after text would otherwise parse as a setext heading. Test in Task 4.
4. **Empty-string CI variables** (`BUILD_NUMBER=''` or `GIT_COMMIT=''`, which Jenkins can produce) must be treated as absent. The stamp then reads `local build`, never `Build # · `. Test in Task 6.
5. **URLs that only look acceptable:**
   - `javascript:` or `mailto:` in `repo`, `liveUrl` or a site link (`z.url()` would let them into an `href`);
   - a scheme-less `github.com/…`;
   - badge `src` values `https://img.shields.io.evil.example/…`, `http://img.shields.io/…` and `https://raw.githubusercontent.com/…`.

   All must be rejected (web schemes only; badges need `https:` and an exact host). Test in Task 2.

  - `siteConfigSchema` and `type SiteConfig = z.output<typeof siteConfigSchema>`.
  - `defineSiteConfig(config: z.input<typeof siteConfigSchema>): SiteConfig`. On failure it throws `Error('Invalid site config:\n' + z.prettifyError(error))`.
- Produces from `yaml-list.ts`: `withPositionalIds(text: string): Array<Record<string, unknown> & { id: string }>`.
  - It parses YAML with `yaml`'s `parse` and adds ids `'000'`, `'001'` and so on in file order.
  - If the YAML isn't a list, it throws `Error('other-projects.yaml must be a YAML list')`.

**Case-study rules** (spec §5.2):
- `title`: string.
- `summary`: string, at most 160 characters.
- `source`: one of `SOURCES`.
- `repo`: `z.httpUrl()`. Required for `public` and `sanitized`; must be absent for `private`.
- `privateNote`: required for `sanitized`; must be absent otherwise.
- `liveUrl`: optional `z.httpUrl()`.
- `stack`: `string[]` with at least 1 item.
- `role`, `period`: optional strings.
- `featured`: boolean, default `false`. `featuredOrder`: integer, required when `featured`.
- `order`: optional integer.
- `badges`: optional `Badge[]`, allowed only for `public` and `sanitized`.
  - `src` is a `z.httpUrl()` refined to protocol `https:` and a hostname of exactly `img.shields.io` or `github.com`.
  - `href` is a `z.httpUrl()`.
- `cover`: optional (the `cover` argument).
- `draft`: boolean, default `false`.

Implement the cross-field rules with `.superRefine`. Each issue is `{ code: 'custom', path: [<field>], message }`, so build errors name the field.

**Site-config rules** (spec §5.1):
- `name`, `jobTitle`, `tagline`, `pitch`: non-empty strings.
- `email`: `z.email()`.
- `links.github`, `links.linkedin`, `links.reelRaffle`: `z.httpUrl()`.
- `cv`: a string starting with `/`.
- `openToWork: { enabled: boolean; message: string }`. `message` must be non-empty when `enabled` (issue path `['openToWork', 'message']`).

**Interfaces:**
- Produces from `case-study-rules.ts`:

  - `type ParsedStudy = { file: string; draft: boolean; featured: boolean; featuredOrder: number | undefined; h2s: string[]; hasPromptMarker: boolean }`.
  - `parseStudy(file: string, source: string): ParsedStudy`.
    1. Split the frontmatter off with `/^---\r?\n([\s\S]*?)\r?\n---\r?\n?/` and parse it with `yaml`. If there is no match or the YAML is invalid, throw `Error('<file>: frontmatter is missing or not valid YAML')`.
    2. Parse **only the body** with `fromMarkdown` from `mdast-util-from-markdown`.
    3. For each depth-2 heading, take its text with `toString` from `mdast-util-to-string`, trim it and replace `’` with `'`.
    4. `hasPromptMarker` is `body.includes('<!-- prompt:')`.
  - `checkStudies(studies: readonly ParsedStudy[]): string[]`. It ignores drafts and returns one message per broken rule, using these exact formats:
    - `More than 3 published case studies are featured: <files joined by ", ">`
    - `featuredOrder <n> is used by more than one published case study: <files>`
    - `<file>: H2 sections must be exactly Context, Problem, Test strategy, Stack, Results, What I'd change (in that order); found: <h2s joined by ", " or "none">`
    - `<file>: remove the scaffold prompt markers (<!-- prompt: … -->) before publishing`
  - `checkDirectories(dirs: readonly string[]): Promise<{ scanned: number; published: number; errors: string[] }>`.

    - It runs `checkStudies` **once per directory**. `src/content/work` and `fixtures/content/work` are separate collections, and `lint` checks both in one call, so pooling them would count Thomas's featured studies and the fixtures' together.

These were found while verifying this plan's toolchain on 2026-10-17. Later plans must deal with them.

- **Script inlining (M2 lightbox, M3 `/quality`).** Astro 7 inlines a processed `<script>` as an inline `<script type="module">` when it has no imports and is under `vite.build.assetsInlineLimit` (4096 bytes by default). `script-src 'self'` blocks that. Astro's `security.csp` hashes go into a `<meta>` policy, but the nginx header policy still applies on top, so they don't help. Set `assetsInlineLimit` (number or function form) so scripts are never inlined, and assert in e2e that there is no inline `<script>`.
- **Placeholder colours (M2, §4.6).** Astro's CSP doesn't hash `style=""` attributes either. Emit the dominant-colour placeholders as a generated stylesheet of per-photo classes from the manifest, not as `style` attributes.
- **YAML dates (M2 `album.yaml`).** Unquoted YAML dates parse to `Date`, so use `z.coerce.date()` or accept `Date`.
- **Markdown images (M3, before Thomas adds diagrams, §4.4).** It hasn't been verified that Astro 7's `<img>` output for images referenced from Markdown is free of `style=`. Add a fixture diagram and assert there are no `style` attributes.
- **`getStaticPaths` (M3 SEO).** `Astro.site` inside `getStaticPaths` is deprecated; use `import.meta.env.SITE`.
- **Playwright image (M4).** Check `docker run --rm mcr.microsoft.com/playwright:v1.64.1-noble node --version` is at least 24.16 before relying on it, because `engine-strict` is on.
- **`astro preview` in other harnesses (M5).** Keep `--ignore-lock` wherever a test harness starts `astro preview`.
